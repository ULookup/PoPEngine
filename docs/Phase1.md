# 第一阶段详细开发方案 · 工程与权威运行时

本阶段交付四个可独立启停的 Linux 进程，以及支持多 Space、多实体绑定的本地权威运行时。正常启动时，每个配置的 Space 从空场开始，按 50 ms 步长独立推进。验收时显式绑定实体并装配测试模块，经真实邮箱观察输入采纳、后台计算和所属分片提交。阶段 2 将沿用进程内投递入口接入 Gateway。范围依据[分阶段开发计划](../DevelopPlan.md)、[系统架构 §5、§11](Architecture.md)和[技术设计 §3–4、§13、§16](TDD.md)。

## 交付顺序

| 工作项 | 前置 | 实现位置与交付物 | 该项完成时可以观察到什么 |
| --- | --- | --- | --- |
| 1. 建立构建入口 | 本机工具链 | 根目录 CMake 工程、Ninja 的 Linux GCC preset、带 baseline 的 `vcpkg.json`、四个 `apps/` 目标和 README 构建说明。选用 C++20，构建产物放入独立目录 | 从新检出的源码和空构建目录，用同一个 preset 生成 `gateway`、`game_worker`、`platform`、`control` |
| 2. 装配进程与配置 | 1 | `engine/core` 放标识、时间类型；`configs/` 放四份本地 YAML；入口使用 yaml-cpp 加载配置，用 spdlog 输出带角色和实例的结构化日志 | 一份合法配置可启动对应进程并等待退出信号。非法角色、缺失预算或重复的 Space 绑定使启动失败，错误指出配置项 |
| 3. 实现邮箱和执行分片 | 2 | `engine/runtime` 实现有界投递、按来源调度、单线程执行循环和关闭；`engine/script` 用官方 Lua C API 管理每个分片的 VM | 投递方获得受理、合并、拒绝或已关闭的明确结果。两个分片在各自线程创建、使用和销毁 VM |
| 4. 独立推进 Space | 3 | `engine/scene` 持有每场的时钟、实体绑定与已提交状态；`services` 按放置配置将 Space 绑定到分片 | 经邮箱发来的完整控制输入，在目标 Space 下一次可处理的 Tick 修改实体。一次调度延迟后能看到逐步追帧及剩余迟到量 |
| 5. 回投计算结果 | 3、4 | 按模块的显式请求派发只读阶段快照，计算线程通过异步结果邮箱回投；在 Scene 分片集中校验身份、阶段与版本后提交 | 当前版本结果更新相应实体；过期结果带原因退出，提交计数和实体状态均可核对 |
| 6. 串起本地验收 | 1–5 | `tests/` 放显式时钟与可控回投的最小场景，使用 CTest 驱动；README 补齐四进程运行、复现场景和退出方法 | 一次本地运行记录能关联输入、Tick、状态和退出；可单独复现满载邮箱与旧结果两种边界 |

### 四个入口如何装配

| 入口 | 本阶段启动内容 |
| --- | --- |
| Gateway | 装配 GatewayService 的进程生命周期和角色配置。公网连接和输入解码在阶段 2 接入。 |
| GameWorker | 装配 PlayerService 与 SceneService，各启一个独立执行分片。SceneService 根据本地配置创建空 Space，运行期间可在各场安装多个实体绑定，Player 分片可空载。每次启动分配可区分本次进程生命期的 `worker_instance_id`。 |
| Platform | 建立 Auth、Social、Chat、Mail、Market、Match、Leaderboard 的模块归属。入口负责配置和生命周期，业务处理随对应开发阶段接入。 |
| Control | 装配 WorldCoordinator 的配置和生命周期。首阶段 Space 放置从本地配置读取，集群目录、租约与交接在后续阶段接入。 |

四个进程均接受 `--config <path>`。先校验角色、分片与 Space 绑定、线程数和队列预算，再创建运行资源，全部就绪才记录 `ready`。收到 SIGINT 或 SIGTERM 后停止接收新工作，唤醒执行循环，在 Tick 安全点停止派发。关闭计算任务入口，等在途生产者停止回投，处理或显式取消已受理项，再释放 Space、分片 VM 和线程，最后刷新日志并退出。关闭期间回投有明确返回；部分启动失败也按已取得资源逆序释放。进程之间无需约定启动顺序。

GameWorker 本地 YAML 至少给出 Player/Scene 分片数、Space 到 Scene 分片的绑定、计算线程数，以及各队列的最大条数、字节数和年龄（毫秒）。固定步长和追帧上限取 TDD 的固定值。`spaces` 的每一项只描述 Space 标识和放置分片。显式空列表表示此 Worker 尚未分配 Space，执行分片可就绪待命。实体、输入数据和验收用的单轴运动规则由测试生产者与场景模块提供。

## GameWorker 的运行路径

1. **路由与单写者。** 可信进程内调用方经 `bindEntity` 发起绑定，控制队列受理后，目标 Scene 分片安装绑定并返回完成回执。普通生产者经 `postInput` 指定 Space、绑定、输入序号、完整控制状态、截止时刻和可选跟踪标识。Scene 按实体独立维护序号与版本，未知实体、错误代次和旧序号在处理时丢弃。同一绑定重复安装保留当前输入水位。
2. **时钟与调度。** 生产用单调时钟计算截止点。每个 Space 保存自己的下一截止点和 `server_tick`，调度器轮流访问到期的 Space。每执行一步，模拟时间和截止点各增加 50 ms。每场单轮最多追两步，仍落后时保留欠账并记录 `tick_lag_ms`，让另一场获得调度机会。较晚创建的 B 从自己的首个截止点起步。
3. **一个 Tick 的提交。** 分片先处理绑定变更并关闭上一 Tick 的结果提交窗口，随后采纳当前输入，清除失效的持续控制，推进本场已装配的模拟模块，最后发布只读运行统计。空场照常计时。测试模块在这个入口计算单轴位移，通用碰撞查询和 Lua 宿主在阶段 4 接入。
4. **工作结果。** 模块按实体和阶段提供独立快照及计算函数。分片记录受理任务的 Space、承载代次、Tick、阶段、状态版本与实体代次。计算线程只读取该快照。在下一提交窗口，Scene 按实体的派发顺序核对任务键与当前版本，匹配结果最多提交一次。每个实体在这条首阶段路径上每步可申请一个任务，多个实体可同时有任务在途；队列拒绝和窗口外回投均有明确处理。

### 邮箱预算与失败语义

控制消息、玩家指令、异步结果、后台任务各有条数、字节数和最大年龄预算。配置校验拒绝缺失或非正上限。入队时同时检查条数和字节；合并按新旧大小更新占用；出队时复核年龄、归属与版本。按 Space 和来源限制单轮消费量，给控制及关键结果留出独立预算。

| 投递内容 | 饱和、过期或关闭时的处理 | 验收证据 |
| --- | --- | --- |
| 连续控制输入 | 同 Space、同一有效绑定及实体的较新完整状态可替换旧状态，旧序号丢弃；替换后超出字节预算则拒绝新项。有效期届满进入停止输入处理 | 实体只使用最新有效序号；持续输入过期后位置停止变化 |
| 离散命令或控制请求 | 保留独立标识。满载时投递方收到拒绝或背压，已受理项完成、过期或取消时给出对应结果 | 填满队列后额外请求收到确定结果；先受理的请求可逐一关联 |
| 异步结果或后台任务 | 入口关闭或满载时向生产者返回原因；明确结束可重算工作。取出时丢弃过期或版本失效的结果 | 队列保持在配置上限内，拒绝和丢弃按原因计数，旧结果不会写入实体 |

日志使用有界异步输出，记录进程角色、实例及事件名；场景事件另附分片、Space、Tick、输入序号或任务版本。每场可读取队列条数、占用字节、最老年龄、合并与拒绝次数、Tick 耗时和迟到量。运行样例只记录复现所需的输入和提交，持续运行按窗口汇总。

## 验收与交接

以下步骤用于实现交付时验收。运行时场景走与 GameWorker 相同的分片、邮箱和提交代码，使用显式时钟或可控的工作完成事件决定时序。

| 场景 | 操作 | 通过条件 |
| --- | --- | --- |
| 干净构建、启动与退出 | 按 README 在独立目录配置和构建。用各自的 YAML 启动四个进程，等到各自就绪，再发送终止信号并有界等待退出 | 四个目标均可独立启动，日志能区分角色和 Worker 实例。空 Space 按时记录 Tick，后台派发和结果提交计数均为零。正常停机退出码为 0；非法配置在就绪前返回非零 |
| 同分片双 Space | A 在 0 ms、B 在 50 ms 加入。给 A 安装两个绑定，向它们投递序号相同、方向相反的控制状态。向空 B 投递一个相同实体的输入，再将调度时刻从 100 ms 推到 250 ms | 在 100 ms，A 已走两步且两个实体各自移动 0.05 米，B 已走一步且绑定数仍为零。每轮每场最多追两步，欠账留给下一轮。控制失效后停止移动，重绑后旧会话输入失效 |
| 真实计算线程 | 通过 `GameWorker::bindEntity` 等候绑定完成，再通过 `postInput` 投递控制状态，等待场景模块报告结果已提交 | 输入经路由、分片、计算池和结果邮箱回到所属分片；未知 Space 与已关闭入口分别返回对应的投递结果 |
| 过期工作结果 | 用同一份起始状态分别运行两次回投。第一次让计算结果携带当前输入版本，第二次让它携带旧版本。两次都经真实邮箱投递，任务仍待提交，身份、Tick 和阶段均匹配 | 第一次提交且派生值更新。第二次记录版本不匹配，实体值和提交版本保持在拒绝前的值；日志可定位原任务和 Space |
| 邮箱的条数、字节和年龄边界 | 用小预算投递同实体的新旧控制状态、不可合并请求及超字节上限的项；显式推进时钟至有效期后再消费 | 可分别观察合并、拒绝、过期三种结果；字节占用随替换正确变化。另一 Space 的消息仍在其预算内被处理 |

阶段交付保留构建 preset、vcpkg baseline、本地 YAML、可复现的测试输入及带 Space/Tick 的关键日志。第一阶段的时钟和邮箱数值用于功能验收；单场 5000 人、集群百万在线与端到端时延另按总计划安排。
